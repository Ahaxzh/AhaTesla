## 1. 背景

### 1.1 生态现状

- **TeslaMate** 是最成熟的自托管 Tesla 数据记录器（Elixir + PostgreSQL + Grafana + MQTT），全球数万用户。它解决了**采集与存储**，但其可视化是 Grafana 仪表盘——面向"看数据"的极客，不面向"生活记账"。
- **tesla-butler**（灵感与核心算法来源）证明了"TeslaMate 数据 → 行程小结/充电提醒/记账/周月报 → 飞书推送"这条路径的真实价值，其**行程边界状态机**与 **FIFO 电价批次账本**是已被验证的核心算法。但它是单人项目：绑定 macOS + 飞书、无 Web UI、无自动化测试、社区基本为零。
- **Teslatlas**（magrathean-uk，Rust 项目家族）验证了"自托管采集 Hub + 本地优先 + 隐私不外传"路线的商业可行性（Open Core：hub/edge/SDK 开源，原生 App 闭源收费）。但其 App 无记账/电费账本能力、单车设计、原生 App 付费且闭源，且用户需自行完成 Fleet Telemetry 授权（门槛高于"已有 TeslaMate 直接连"）。
- TeslaMate 生态中，"Grafana 深度图表"与"生活化记账 + 主动推送"之间存在**市场空白**，且无人以"不绑 IM、不绑地区"的开源方式做好它。

### 1.2 机会

AhaTesla 以自托管 Web 应用形态填补该空白：向导式接入 TeslaMate，把用车数据变成**账本与报告**，通过 **Web Push / Telegram / 飞书**多渠道触达用户。对 TeslaMate 存量用户提供**零迁移成本**的接入方式（connect 模式），构成天然获客杠杆。

### 1.3 现有基础

仓库中已存在一夜生成的骨架：Node 22 零框架后端 + React 19 PWA 前端 + Playwright E2E + socat 桥接部署方案，已移植 tesla-butler 两大核心算法。**本 PRD 以该骨架为基线演进**，但其"功能存在"≠"功能可用"，M0 必须先验证。

## 2. 产品定位与目标

### 2.1 一句话定位

> 自托管的 Tesla 用车助手：把 TeslaMate 的数据变成行程账本、电费报告与贴心提醒，推到你的手机上。

### 2.2 v1 目标（按优先级）

1. **G1 双模开箱即用**：全新用户用全栈 compose 十分钟内从部署到看到自己的车；存量 TeslaMate 用户 5 分钟内完成接入。
2. **G2 记账可信**：行程电费采用 FIFO 批次分摊算法，账本能对得上"我到底花了多少钱"，含油车费用对比。
3. **G3 通知触达**：Web Push（默认、零第三方依赖）+ Telegram + 飞书三渠道，实时事件与周/月报告全量进 v1。
4. **G4 开源发布水准**：Docker 一键部署、中文文档优先 + i18n 架构预留、清晰的安全边界、MIT 合规。
5. **G5 骨架可演进**：现有代码经 M0 验证后作为基线，不推倒重写。

### 2.3 非目标（v1 明确不做）

- ❌ 车辆控制命令（开空调/锁门/充电启停）——永久红线
- ❌ 多账户/多用户体系（单账户制：每实例一个账号，首个注册即管理员；数据结构预留）
- ❌ 自建 Tesla Fleet API 对接（授权永远发生在 TeslaMate 内，本应用不碰 Tesla Token）
- ❌ 替代 Grafana 的极客级原始监控面板（高频 BMS 遥测、散点拟合与多维交叉下钻留给 Grafana；AhaTesla 仅提炼生活化的轻量趋势摘要，如满电续航平滑趋势）
- ❌ 英文本地化 UI（v1 中文优先，架构按 i18n 设计，英文 v1.x）
- ❌ 云端 SaaS / 任何数据上云

## 3. 目标用户

### 3.1 Persona A —— "存量极客"（connect 模式）

已自建 TeslaMate（NAS/小鸡/VPS），有 Docker 基础。诉求：**不迁移、不折腾**，给现有栈加一层记账与推送。对"改我的 compose / 动我的数据库"高度敏感——必须零侵入、只读。

### 3.2 Persona B —— "新手上路"（全栈模式）

刚买 Tesla 或刚知道 TeslaMate，有基本 Docker 能力但不熟悉 Elixir/Postgres。诉求：**一条命令、一个向导**，从零到看到自己的行程账单。Tesla 授权、电价配置越少手动步骤越好。

### 3.3 反向画像（v1 不服务）

希望一个账号管理多辆车/全家人的用户；希望手机 App Store 原生应用的用户；不想自托管任何东西的用户。

## 4. 核心用户旅程

### 4.1 首次部署与引导（Onboarding Wizard）

```
Docker 部署 → 打开 Web → 注册首个账号（即管理员）
  → 向导第1步：选择接入模式
      A) 我已有 TeslaMate → 填 Postgres 连接信息
         → 连接测试（含只读权限校验）→ 发现车辆 → 完成
      B) 我是新用户 → 使用全栈 compose
         → 向导深链跳转 TeslaMate 登录页完成 Tesla 授权
         → 轮询 cars 表 → "✓ 已发现你的 [车型]" → 完成
  → 向导第2步（可选，可跳过）：配置默认电价 + 常用充电点电价
  → 向导第3步（可选，可跳过）：开启 Web Push（PWA 权限询问）/ 接入 Telegram / 飞书
  → 进入仪表盘（已有数据即刻可见）
```

**关键规则**：每一步皆可跳过、可事后在设置中补做；向导未完成也可进入只读预览态（看到"等待接入数据源"的引导页）。

### 4.2 日常使用

- **被动接收**：行程结束推送小结（里程/耗时/电费/油车对比）；充电开始/完成推送；每周一上午周报、每月 1 号月报。
- **主动查看**：仪表盘（车辆状态、本月统计、最近行程/充电）；行程列表与详情（路线图）；充电列表与按站点统计；电价与账本设置。

## 5. 用户故事与验收标准

> 格式：US-{n}。每条 AC 均为可测试断言。优先级 P0=v1 必须，P1=v1 尽量，P2=v1.x。

### 5.1 部署与账户（Domain: Deploy & Auth）

**US-1 全新用户一键部署**（P0）
作为新用户，我想用一条 `docker compose up` 命令拉起包含 TeslaMate + AhaTesla 的完整栈，以便零基础开始使用。
- AC-1.1 官方 `docker-compose.yml`（全栈版）单命令启动后，访问 AhaTesla Web 端返回 200 且可注册
- AC-1.2 全栈版自带 Grafana（`profiles: [full]`，默认启用）；`--profile` 关闭后其余功能不受影响
- AC-1.3 全栈版自动为 AhaTesla 创建 Postgres **只读用户**，应用侧无 superuser 权限
- AC-1.4 无预设明文密码：首个访问 Web 端的用户进入 `/setup` 页面注册管理员账号，**首位注册即管理员，注册完成后该路由自动关闭**；不依赖容器日志打印初始密码

**US-2 存量用户零侵入接入**（P0）
作为已有 TeslaMate 的用户，我想只填数据库连接信息就完成接入，不想改动现有任何容器。
- AC-2.1 文档提供"已有 TeslaMate"路径：建只读账号 SQL + 连接信息填写指引，全程**不修改**用户现有 compose
- AC-2.2 向导中填入连接信息后，系统做 4 项校验并逐项反馈：可达性 / 凭据 / teslamate 库存在 / 只读权限
- AC-2.3 校验通过后 60 秒内在 `cars` 表发现车辆，向导显示"✓ 已发现你的 [车型名]"；**cars 表行数 > 1 时（换车/双车家庭），向导展示车辆选择器**（默认选中最近有行程的 car_id），本地 SQLite 所有核心表绑定 `car_id` 字段做数据隔离，防止多车数据串进同一个 FIFO 池
- AC-2.4 应用对 teslamate 库的任何 SQL 均为只读；**只读校验采用元数据探测**：`SELECT has_table_privilege(current_user,'public.drives','INSERT,UPDATE,DELETE,TRUNCATE') OR has_schema_privilege(current_user,'public','CREATE')`，返回 true 即中断启动并要求降级只读账号；**严禁用 CREATE TABLE/INSERT 实写探测**（TEMP 表对 PUBLIC 默认有权限会误杀标准只读账号，普通表则会在报错前真写脏数据违反红线）；连接池每个 Session 初始化时强制 `SET default_transaction_read_only = on`（会话级双保险）

**US-3 首个账号注册与管理员即位**（P0）
作为部署者，我想注册第一个账号并自动成为管理员，之后关闭注册入口。
- AC-3.1 首个注册账号自动具备管理员身份；此后注册入口默认关闭（可在设置中显式重新开放）
- AC-3.2 登录态 JWT httpOnly cookie + **30 天长效会话（Refresh Token 机制）**，避免 PWA 隔天频繁掉登录态；支持登出、修改密码与手动吊销所有会话
- AC-3.3 连续 5 次登录失败触发限速（≥15 分钟锁定），错误提示不泄露"用户名不存在 vs 密码错误"
- AC-3.4 所有 `/api/*` 受保护端点未认证访问返回 401 `{error:{code,message}}`

### 5.2 数据接入与车辆发现（Domain: Data）

**US-4 Tesla 授权经由 TeslaMate**（P0）
作为新用户，我想在向导中被引导到 TeslaMate 页面完成 Tesla 登录，而不把 Tesla 密码给 AhaTesla。
- AC-4.1 全栈模式下向导提供跳转 TeslaMate 登录页的深链/内嵌指引；**TeslaMate Web(4000) 无密码保护，严禁映射公网端口**——标准方案：4000 仅 Docker 内网可达，由 AhaTesla 在管理员鉴权下提供反代路由（同域丝滑授权 + 替 TeslaMate 补上认证）；兜底方案：默认 `127.0.0.1:4000:4000` + 向导旁红色安全警告。应用自身**不出现任何 Tesla 账号密码输入框**
- AC-4.2 代码库中不存在 Tesla Fleet API 客户端与 Token 存储逻辑（架构红线，代码审计项）
- AC-4.3 TeslaMate 完成授权后，AhaTesla 在 120 秒内检测到新车辆并推进向导

**US-5 数据源健康可见**（P1）
作为用户，我想随时看到 TeslaMate 连接是否正常、数据新鲜度如何。
- AC-5.1 系统状态页显示：DB 连接、最近一次行程时间、累计行程数；仅在 MQTT 已配置时显示 MQTT 连接项（MQTT 为可选增强，见 §7.1）
- AC-5.2 数据源异常（DB 断连 > 2 分钟）时在 Web 端顶部横幅告警，并（若已配置）发送一条告警推送

### 5.3 行程与账本（Domain: Trips & Ledger）

**US-6 行程列表与详情**（P0）
作为车主，我想浏览每一次行程的里程、时长、能耗、电费与路线。
- AC-6.1 行程列表支持分页与时间范围筛选；字段含起止时间/里程/时长/能耗/kWh每百公里/电费
- AC-6.2 行程详情含路线图（polyline 点集渲染）与起终点地址；数据不足时显示空态而非报错
- AC-6.3 行程耗电 = `(start_rated_range_km − end_rated_range_km) × cars.efficiency`（表显净耗电；rated 缺失时回退 ideal_range 同式计算）；可选用起止 `positions.battery_level` 差值 × 电池可用容量校核；UI 标注计算口径。**注：TeslaMate `drives` 表无 `power_consumed_kwh` 字段，不得假设其存在**

**US-7 FIFO 电价批次账本**（P0）
作为精打细算的车主，我想让每次充电实际花的钱按批次摊到后续行程上，得到真实每公里成本。
- AC-7.1 充电会话计价优先级（**四层回退**）：① AhaTesla 本地手动录入费用（SQLite `charge_cost_overrides` 表）→ ② `charging_processes.cost` 非空 → ③ geofence 单价计算 → ④ 用户默认价
- AC-7.2 **FIFO 批次入池公式（含充损闭合）**：批次可用电量 = `charge_energy_added`（电池净吸收）；批次折算单价 = 该次充电实付总额 ÷ `charge_energy_added`（含充电损耗的有效单价）。批次全部耗尽时分摊电费总和 ≡ 用户实付总额（账本闭合）。P3 批次表提示"单价已含充电损耗折算"
- AC-7.3 默认电价变更只影响之后的新行程；**设置页提供【重算历史账本】按钮**（可选时间范围/全量，按当前规则显式重算，进度可见）；变更历史可查
- AC-7.4 月度统计：里程 / 电费 / 油车费用对比（默认基数：百公里油耗 8.0L × 油价 8.20 元/L ≈ 0.656 元/公里，可在【系统设置 → 账本参数】自定义；周/月报卡片注明"对比基准：8.0L/100km @ 8.2元/L"）
- AC-7.5 **驻车损耗分摊（事件驱动扣减）**：每次新事件（新行程或新充电）发生时，对比"上一事件结束时表显续航/电量"与"当前事件开始时表显续航/电量"，差值 **> 0.5 kWh** 立即生成一条`驻车能耗支出`冲抵当前 FIFO 批次（不等下次充电，避免滞后错价）；差值 ≤ 0.5 kWh（含 BMS 温漂导致的负数）忽略。单测覆盖：纯哨兵期间/行程哨兵交替/损耗超过批次余额/负损耗过滤
- AC-7.6 **账本修正窗口**：推送小结发出后即固化（快照不可变）；最近 7 天内补录充电实际费用（P4 详情内【录入实付电费】，存本地 SQLite `charge_cost_overrides`）时，账本异步重算受影响行程，UI 标注"已依据实际充电发票校准"；重算不重复推送

**US-8 充电账本与站点统计**（P0）
作为车主，我想看每个充电站的电量、花费与单价对比。
- AC-8.1 充电列表字段：起止时间/地点/充入电量/费用/单价/起止电量/时长/峰值功率
- AC-8.2 按站点聚合统计：次数/总电量/总费用/平均单价，支持 month/all 两种周期

**US-9 多币种计价**（P1）
作为海外用户，我想以本地货币与电价单位记账。
- AC-9.1 货币符号、电价单位（元/kWh、$/kWh 等）可配置；API 契约中不再出现 `costCny` 类硬编码命名（迁移为 `cost` + 实例级货币配置）；**金额字段保留 2 位小数、单价字段保留 3~4 位小数**（见 §7.3 精度规范）
- AC-9.2 v1 实现人民币默认 + 单位符号可配；汇率换算不在 v1 范围

### 5.4 通知与推送（Domain: Push）

**US-10 推送渠道抽象**（P0）
作为用户，我想自由启用 Web Push / Telegram / 飞书任意组合，各渠道可独立开关与测试。
- AC-10.1 后端存在统一 `Notifier` 接口，三渠道为独立实现；新增渠道不改规则引擎
- AC-10.2 每渠道提供"发送测试消息"按钮，配置后可立即验证连通性
- AC-10.3 渠道配置（如飞书 appSecret、Telegram Bot Token）AES-GCM 加密落盘（密钥来源见 §7.2 `APP_SECRET_KEY`），API 永不回传明文

**US-11 Web Push（默认渠道）**（P0）
作为用户，我想把 PWA 装到手机桌面后直接收通知，不依赖任何第三方 IM。
- AC-11.0 **环境前置检测**：应用检测当前上下文是否为 secure context（HTTPS）；非 HTTPS 环境下 Web Push 选项置灰并提示"当前为非 HTTPS 环境，Web Push 不可用，建议配置反代启用 HTTPS 或优先绑定 Telegram / 飞书"
- AC-11.1 iOS 16.4+（添加到主屏幕后）与 Android Chrome 均可收到推送；桌面浏览器可收
- AC-11.2 通知点击跳转到对应详情页（行程详情/充电详情/报告页）
- AC-11.3 用户在浏览器撤销通知权限后，应用停止向该订阅推送并清理失效订阅

**US-12 实时事件推送**（P0）
作为车主，我想在行程结束、充电开始/完成时收到即时小结。
- AC-12.1 五类事件（tripEnd / chargingStart / chargingDone / weekly / monthly）各自可独立开关
- AC-12.1a 行程边界判定采用状态机语义，继承已移植算法；单测覆盖"停车未熄火""信号丢失""跨天行程"边界
- AC-12.1b 事件捕获基线为 PostgreSQL 轻量轮询（15~30 秒，见 §7.1）；配置了 MQTT 时切换为事件驱动，两者推送结果一致；**首次接入数据源时立即写入通知游标水线（当前最大 drives.id 与 charging_processes.id）——水线之前的历史数据仅静默账本建档，严禁触发任何推送（防历史推送风暴）**
- AC-12.2 同一事件多渠道启用时全部送达；单渠道失败不影响其他渠道，失败记录进事件日志
- AC-12.3 推送在 **TeslaMate 完成事件结算落库**（drives/charging_processes 的 end_date 非空且状态机确认闭合）起 60 秒内发出（Web Push / Telegram / 飞书各自计时；不含状态机防抖静默期——该期为业务必需，不算 SLA 违约）

**US-13 周报与月报**（P0）
作为车主，我想每周一收周报、每月 1 号收月报，汇总里程/能耗/电费/对比。

## 6. 页面与交互规格（Page & UI Specifications）

> 设计总纲：**"汲取 Grafana 的核心洞察，剔除其极客冗余，重塑为移动端/生活化友好的轻量图表。"** Grafana 图表密集、偏向运维监控；AhaTesla 需要的是一眼看懂、交互流畅、紧扣用车与花销。

### 6.1 全局布局与响应式原则

应用采用**移动优先（Mobile First）**架构：

- **桌面端（≥ 1024px）**：左侧固定侧边栏（含车辆缩略状态、导航链接、系统健康指示灯）+ 顶部轻量栏（当前账本周期、刷新状态、登出）；主内容区网格布局，最大宽度 1280px 居中
- **移动端 / PWA（< 1024px）**：顶部精简状态栏 + 底部 4 项 TabBar（**概览 / 行程 / 充电 / 设置**）；单列卡片流，支持下拉刷新
- **全局状态反馈规范**：
  - **骨架屏**：数据加载超过 150ms 必须展示骨架占位，严禁整屏白屏
  - **全局异常横幅**：TeslaMate 数据库失联 > 2 分钟时，全站顶部常驻黄底横幅"TeslaMate 数据库连接中断，当前展示离线缓存数据"

### 6.3 核心页面详细规格

#### P1 初始化向导（`/setup`）

- **前置**：系统检测到本地库无管理员账号时强制重定向至此；完成后路由锁定（403）
- **形态**：居中分步向导，支持进度保存
- **Step 1 创建管理员**：用户名 + 密码（≥8 位强度校验）+ 确认密码；提交后自动登录
- **Step 2 数据源接入（双模分支）**：
  - 模式 A（存量接入）：PostgreSQL Host / 端口（默认 5432）/ 库名（默认 `teslamate`）/ 用户名 / 只读密码
  - 模式 B（全栈模式）：提示"检测到同栈部署"，显示跳转 TeslaMate 授权的外部链接按钮 + 车辆发现轮询指示器
  - 【测试并验证】按钮触发**渐进式四级检查**：网络可达 → 数据库认证 → 只读安全校验（探测写入并强制阻断）→ 检索车辆数据（cars 表）；全绿后显示"✓ 已成功接入车辆：[车型]"，【下一步】亮起
- **Step 3 账本初始化（可跳过）**：默认电价（预填 0.60 元/kWh）、油车基准（预填 8.0L/100km @ 8.20 元/L）
- **Step 4 通知渠道（可跳过）**：HTTPS 环境显示【一键开启 Web Push】；HTTP 局域网显示提示卡片引导配置反代或绑定 Telegram/飞书；【完成向导】→ 跳转 `/`

#### P2 仪表盘（`/`）

- **模块 1 车辆实时状态卡片**：车名/车型、状态胶囊（行驶中/充电中/哨兵开启/睡眠中）、电量百分比（>20% 绿、≤20% 橙、≤10% 红的电池图形）与表显续航、状态持续时长（如"已睡眠 4 小时 12 分钟"）、"数据同步于 1 分钟前"
- **模块 2【Grafana Timeline 提炼】24 小时状态时间轴**：将 Grafana 甘特图简化为"彩色胶囊时间条"（类 iOS 屏幕使用时间）——行驶（蓝）/充电（绿）/哨兵·驻车（橙）/睡眠（紫）/离线（灰）；触控色块显示 Tooltip（"08:15~09:02 行驶 47 分钟，耗电 12%"）；底部 24h 占比汇总（"今日行驶 1.5h · 充电 1.2h · 睡眠 18.3h"）

- **模块 4【Grafana Mileage 提炼】用车日历热力图**：参考 GitHub 贡献图，最近 3 个月矩阵网格（横轴周、纵轴星期），颜色深度 = 当天行驶里程；点击格子筛选当日全部行程卡片

### 6.5 前端图表工程约束

1. **图表库选型**：轻量 SVG/Canvas 移动友好库（Chart.js / uPlot / Recharts/Tremor 候选，架构评审定），包体积增量 **< 150KB (gzipped)**，严禁引入 Grafana 原生前端组件
2. **移动端手势**：曲线图禁用页面级双指缩放，改内置单指水平拖拽擦动（Scrubbing）；Tooltip 移动端吸顶/吸底固定，严禁遮挡折线
3. **数据降采样**：长途行程 positions 点集可达数千点；API 或渲染层必须采用 **LTTB 算法**降采样，单图折线渲染点数 **≤ 300**，确保低端手机 60 FPS 滑动
4. **地图坐标系规范**：TeslaMate positions 存 WGS-84 原始坐标；底图源可配置（默认选国内可达瓦片源）。**当底图为 GCJ-02 系（高德/腾讯）时，轨迹渲染前必须做 WGS-84→GCJ-02 纯本地数学转换**（零外部请求，几行公式）；底图为 WGS-84 系（OSM 系）时直绘。严禁将 GPS 坐标发往外部转换服务

## 7. 非功能需求

### 7.1 架构基线（v1.1 新增）

- **自身持久化存储**：AhaTesla 自有数据（账号凭据、加密的渠道密钥、Web Push 订阅、电价规则、FIFO 批次消耗记录、报告快照、事件日志）存储于**本地 SQLite**（单文件，卷挂载规范 `/data/ahatesla.db`）。**严禁写入 TeslaMate 库**。
- **事件捕获策略（解耦）**：
  - **基线机制（全模式默认）**：PostgreSQL 轻量轮询——每 15~30 秒查询 `drives` / `charging_processes` 的结算状态变化，满足 60 秒推送时效，对存量库零侵入、零额外端口；
  - **增强机制（可选）**：MQTT 订阅仅在用户显式配置时启用（全栈模式可默认开启），用于更快感知充电状态变更；未配置时系统状态页不显示 MQTT 项，**不作为存量用户的强制接入项**。
- **连接方式分级**：connect 模式标准方案为 ① 同机 Docker external network 直连；② 跨机局域网 IP 直连（附只读账号 SQL 指引）。socat 桥接仅作为高级附录存在，不进主线文档。

### 7.2 安全

- teslamate 库只读（红线）；只读校验 = `has_table_privilege()` 元数据探测 + 每连接 `SET default_transaction_read_only = on` 会话锁（详见 AC-2.4，严禁实写探测）
- 不实现任何车辆控制命令（红线）；代码库中不存在 Tesla Fleet API 客户端与 Token 存储
- VIN/GPS/Token/Secret 不进 Git/日志/错误信息（红线）
- 渠道密钥 AES-256-GCM 加密落盘，密钥来自 `.env` 的 `APP_SECRET_KEY`；若缺失则启动期生成并提示持久化保存
- 仅监听内网/经反代 HTTPS 暴露

### 7.3 性能与精度

- 10 万条行程规模下，仪表盘首屏 API P95 < 800ms（含批次账本计算）；重查询走索引（由架构评审定具体索引方案）
- **金额精度规范**：API 金额字段统一保留 2 位小数；单价字段统一保留 3~4 位小数（如 0.455 元/kWh）；账本内部计算用高精度，仅在展示层截断

### 7.4 可靠性

- 推送单渠道失败不阻塞其他渠道；进程崩溃重启后状态自愈（状态可从 teslamate 库 + 本地 SQLite 重建）
- **账本修正窗口**：推送小结为不可变快照；账本数据允许最近 7 天内因补录充电实际费用异步重算，UI 标注"已依据实际充电发票校准"

### 7.5 可测试性与兼容性

- 延续现有纪律——每个页面/按钮/双视口 E2E；live 测试连真库但只读可跳过；提交前全绿
- Postgres 17（TeslaMate 现行）；TeslaMate schema 变更时有启动期表结构校验并给出可读错误
